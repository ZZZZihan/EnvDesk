# EnvDesk

面向 Python 环境与依赖问题的排障 Agent 项目。

**当前状态：仅完成项目初始化。** 仓库现有内容是 Python 包入口、构建元数据与开发文档；诊断工具、文档检索、LangGraph 编排、数据库、API、页面和评测程序均尚未实现。下文的功能与验收标准是开发目标，不是已交付能力。

**开发规格：[EnvDesk Code Design Spec 1.0](docs/spec-v1.0.md)。** 模块、数据结构、工具/API 契约、任务副本、确认与恢复、验收矩阵以该规格为实现依据。规格已形成文档基线，功能与验收仍待完成。

**首要设计原则：AI native。** 从用户目标、证据上下文、工具与执行反馈出发设计排障任务。Agent 自主选择取证、检索、追问和计划，并依据新事实调整判断；程序保证执行边界、持久状态和独立验证。五类故障用于限定能力与评测范围，不按案例编号写死诊断路线。完整原则见 [Spec §1.2](docs/spec-v1.0.md#12-ai-native-首要原则)。

## 项目要解决的问题

开发者提供错误日志、项目配置和复现条件。EnvDesk 的目标是收集环境事实、检索相关官方文档、提出有证据的处理方案，并在用户确认后对演示副本执行受限操作，最后验证问题是否解决。

首版聚焦五类故障：

| 故障类别 | 需要核对的事实 |
| --- | --- |
| Python 版本不满足项目约束 | 项目声明与实际解释器版本是否兼容 |
| 虚拟环境或解释器选错 | 安装和运行是否使用同一环境 |
| 依赖缺失或未同步 | 依赖声明、安装状态与运行目标是否一致 |
| 依赖声明与锁文件不一致 | 配置变更是否要求重新锁定或同步 |
| 可选依赖未启用 | 当前任务需要的 extra 是否已声明并启用 |

首版将固定一种 Linux 演示环境，记录 Python、uv 与依赖的实际版本。现阶段尚未固定 uv 版本，也未提供 Docker 环境和依赖锁文件；这些在故障复现阶段补齐。

首版范围是预设演示项目、文本日志与配置，以及预定义操作集合。GPU/CUDA、任意企业仓库、任意 shell 执行、完整 IDE、OCR、跨平台覆盖和多智能体均不在首版范围内。

## 计划输入与输出

输入计划包含：问题描述、`case_id`、原始命令与日志、配置文件、允许读取的环境信息。条件不足时应追问，而不是猜测。

输出计划包含：

- 诊断结论及对应的环境证据；
- 支持结论的文档链接、片段和适用版本；
- 候选操作、确认状态与未解决项；
- 验证输出、实际变更以及最终状态。

所有处理都将围绕演示副本进行。原始案例与参考答案不会交给模型任意修改。

## 三个计划工具

| 工具 | 输入摘要 | 目标行为 |
| --- | --- | --- |
| `search_docs` | `query`、`tool_version` | 检索固定文档集，返回带来源和版本的片段 |
| `inspect_case` | `case_id`、`check_type` | 只读检查解释器、配置、依赖、锁文件或 extras |
| `verify_candidate` | `case_id`、`plan_id`、`approval_id` | 校验已存储计划和确认，在副本执行允许的操作，并运行固定验证 |

模型选择检查或检索步骤；程序负责参数校验、权限边界、确认、执行和结果记录。诊断阶段向模型开放前两个工具，`verify_candidate` 在有效确认后由固定执行节点调用。工具签名与状态语义见 [Spec 1.0](docs/spec-v1.0.md) 和 [架构概览](docs/architecture.md)。

## 技术规划与实际依赖

| 组件 | 计划用途 | 当前状态 |
| --- | --- | --- |
| Python ≥ 3.12 | 配置解析、工具与应用代码 | 已声明版本要求；仅有包入口 |
| Pydantic | 工具参数与结果校验 | 待引入 |
| LangGraph | 状态编排、条件路由、中断与继续 | 待引入 |
| SQLite | 计划、确认、执行记录及本地状态 | 待实现；业务库与 `langgraph-checkpoint-sqlite` 检查点库分开 |
| FastAPI | 提交任务、查询状态、确认和读取结果 | 待引入 |
| FTS5/BM25 词法检索 | 固定官方文档快照 | 待实现；embedding 仅在有具体漏检时做开发集对照 |
| pytest、Docker | 关键行为验证与固定演示环境 | 待引入 |

当前 `pyproject.toml` 的应用依赖为空，仅声明 setuptools 构建后端。每项依赖将在对应代码进入仓库时加入并记录版本，避免让依赖列表暗示已实现的能力。

## 当前可执行的安装与检查

以下命令只安装和检查初始化包；目前没有 CLI、HTTP 服务或 Agent 启动命令。

在当前仓库根目录执行：

```bash
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
python -c "import envdesk; print(envdesk.__version__)"
```

要求解释器版本为 3.12 或更高。安装时可能需要获取构建依赖；当前版本字符串只用于包元数据，不代表功能完成度。

`.env.example` 提供未来模型接入的空值配置名称。当前代码不会读取这些变量，也不需要 API Key；不必为初始化包创建 `.env`。

## 首个可执行开发任务

**P0-01：复现一个真实故障，并明确机器可以验证的成功条件。**

1. 选择“虚拟环境或解释器选错”或“依赖缺失或未同步”中的一个最小问题。
2. 在后续新增的 `examples/` 中保存最小项目和复现说明；记录 Python、uv、操作系统版本、触发命令与原始输出。
3. 在干净副本人工复现，再人工修复；用固定的导入或应用检查确认恢复，并记录配置与文件变化。
4. 将起始输入、参考答案和验证器分开组织；参考答案不能成为未来 Agent 可读的输入。
5. 实现只读的 `inspect_case` 首个检查分支，随后立即接入真实模型，打通首例的自主取证、计划确认与验证闭环；完整检索和页面随案例需要补齐。

**完成判据：**同一初始项目至少两次重建能重现同一故障，参考修复能通过同一验证器；只读检查不修改案例。此时再将任务标记完成。

详细任务依赖、P0/P1 及验收见 [开发路线](docs/roadmap.md)。

## 计划评测方式

先制作和人工核验少量可复现案例，再按原始项目或根因实例划分开发与测试分组。约 10 个开发案例、20 个正式修复案例是后续规模目标，不是现有数据数量。

比较固定诊断规则脚本与完整 Agent，使用相同初始材料、允许操作、可访问证据和预算约束。依据开发集做改进，冻结改进前后版本后再对预留测试集做正式比较。

修复必须由独立验证器判断；超时、无结果和验证失败保留在分母中。缺少信息、用户拒绝和越界请求另设行为验证集。完整口径见 [评测规范](docs/evaluation.md)。

**当前没有评测集、完成率、性能数据、模型运行记录或真实用户试用结果。**

## 与 MiniLoop 的关系

EnvDesk 是任务导向的应用项目，计划直接使用 LangGraph。MiniLoop 是独立的工具调用运行时学习项目。两者可以共享工具协议的理解和日志字段设计，但 EnvDesk 不要求安装 MiniLoop，也不嵌套第二套编排循环。
