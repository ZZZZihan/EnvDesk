# 架构设计

**状态：设计草案，尚未实现。** 当前可执行内容仅为包导入；本文的模块、流程、字段、工具和存储结构均是后续开发约定。

## 1. 任务边界

输入是一个预设演示案例及其问题描述、命令、日志和配置。目标是形成“证据—判断—候选方案—确认—验证”的完整记录。

首版固定一种 Linux 环境，具体 Python、uv 和依赖版本在首批故障复现后记录。一个案例只有一个受限工作区；原始模板只读，所有候选操作应用到由程序创建的副本。参考答案和独立验证器位于模型不可访问的位置。

五类故障以 README 定义为准。首版不接收任意用户仓库路径、不开放任意命令执行，也不引入多租户服务或分布式任务系统。

## 2. 计划模块

以下路径是拟定的代码组织方式，当前尚未创建。

| 拟定模块 | 职责 | 进入仓库的时机 |
| --- | --- | --- |
| `schemas.py` | 输入、事实、计划、确认和结果结构 | 首个真实工具实现时 |
| `cases.py` | 案例登记、路径解析与只读材料访问 | 首批复现案例完成后 |
| `tools/inspect.py` | 受限的环境与配置检查 | P0-02 |
| `tools/search.py` | 文档检索与来源返回 | P0-03 |
| `tools/verify.py` | 确认校验、预定义操作与固定验证 | P0-04 |
| `workflow.py` | LangGraph 状态、路由与终止 | P0-05 |
| `storage.py` | SQLite 业务记录 | P0-06 |
| `api.py` | FastAPI 任务与确认接口 | P1-01 |

计划采用一个模型适配，不预先抽象多供应商平台。文档量较小时先做词法检索；一种 embedding 检索作为开发集对照，是否保留由结果决定。

## 3. 流程与状态

计划流程为：验证输入 → 收集事实 → 必要时检索或追问 → 形成方案 → 等待确认 → 在副本验证 → 汇总结果。

收集事实与检索阶段允许模型在三个工具中选择下一步。修改前的确认、执行边界和结果保存由程序固定控制。验证失败后，只有在预算允许且存在新的证据时才继续诊断；否则返回未解决项。

| 计划状态 | 含义 | 允许的后续动作 |
| --- | --- | --- |
| `collecting` | 检查环境、检索证据 | 继续检查、追问、生成方案或结束 |
| `needs_input` | 缺少复现或环境信息 | 用户补充后重新收集事实 |
| `awaiting_approval` | 计划已保存，等待确认 | 确认、拒绝或因材料变化重新规划 |
| `verifying` | 已通过确认校验，正在操作副本 | 记录验证结果或进入状态核查 |
| `needs_reconciliation` | 操作是否完成无法确定 | 查询实际副本状态与执行记录 |
| `resolved` | 固定验证通过且约束保留 | 返回结果 |
| `unresolved` | 验证失败、预算耗尽或无法继续 | 返回已有证据与未解决原因 |
| `cancelled` | 用户拒绝或主动结束 | 返回已有记录 |

上述状态用于明确语义，实际字段与枚举将在实现时与测试一起固定。模型回复“成功”不能直接将任务标为 `resolved`。

## 4. 三个工具的计划契约

所有工具共用的返回信息拟包含：`call_id`、`case_id`、执行状态、结构化数据、原始输出摘要、耗时和可解释错误。原始输出设大小限制；超时、未知操作和参数错误必须可区分。

### search_docs

- 输入：查询文本与案例使用的工具版本。
- 数据：固定的官方文档集合，每条文档保留 URL、标题、采集时间、适用版本和内容哈希。
- 输出：片段 ID、标题层级、原文片段、来源 URL、版本及检索分数。
- 无证据或无法确认版本适用性时明确返回，不拼造来源或推测适用版本。

文档内容可作为事实来源，但不能修改工具白名单或确认策略。来源登记见 [REFERENCES.md](../REFERENCES.md)。

### inspect_case

- 输入：已登记的 `case_id` 与枚举 `check_type`。
- 计划检查类型：`python_version`、`interpreter`、`dependencies`、`lock_state`、`extras`。
- 程序将案例 ID 解析为允许路径；模型不直接指定任意文件系统路径。
- 返回实际解释器位置与版本、配置字段、安装状态或检查输出，并标记无法取得的字段。
- 只读检查不得同步依赖、改写锁文件或自动安装软件。

每个检查类型只在实现后加入允许列表。未实现类型应返回明确的“不支持”结果，不能返回伪造成功数据。

### verify_candidate

- 输入：`case_id`、`plan_id`、`approval_id`。
- `plan_id` 指向服务端已保存的不可变候选计划；操作枚举与参数从该计划读取，模型不能通过此次调用临时换入新命令。
- 先验证计划属于当前案例、确认未过期、计划内容与相关文件状态均未变化，再建立或访问演示副本。
- 只执行已实现的操作枚举，运行预先登记的验证入口，返回实际差异、输出和通过/失败原因。

首版拟定的操作类型是：选择已允许的解释器、同步已声明依赖、启用已声明的 extra、在原有约束下更新锁文件。具体参数、前置条件和版本组合须随案例验证后固定；操作尚未实现前不向模型开放。

程序应通过明确参数列表调用受限程序，不把模型生成的字符串交给 shell。允许修改的文件、执行时限和测试入口由案例配置决定。不得通过删除功能、放宽项目约束、改写验收测试来取得“修复成功”。

## 5. 状态、确认与副作用

计划保存下列业务对象：

| 对象 | 需要保存的核心信息 |
| --- | --- |
| 案例 | 原始模板、版本、允许操作、当前副本标识 |
| 任务 | `task_id`、当前状态、累计预算、图运行标识 |
| 计划 | `plan_id`、操作列表、参数、相关文件哈希 |
| 确认 | `approval_id`、计划内容哈希、确认时材料状态、确认结果 |
| 执行 | 操作请求标识、开始/完成状态、输出、结果与实际变更 |

确认是对特定计划和材料状态的同意。确认后若配置、计划或操作参数改变，原确认失效，需重新确认。

已完成的重复执行请求应返回已有结果。若只记录了“开始”但没有可靠完成结果，先进入 `needs_reconciliation` 查询实际状态；不得直接把整个操作重跑。

业务记录计划使用 SQLite。LangGraph 的持久化检查点采用与选定版本兼容的本地组件；即使共用 SQLite 存储介质，图状态与业务执行记录仍需分别定义。

持久化的首个验收目标是“等待确认时结束进程，重启后以同一任务标识继续”，并验证两个任务互不串状态。检查点本身不保证业务副作用只执行一次；中断恢复可能重入节点，执行边界与重复请求处理必须另行验证。官方行为依据见 [LangGraph 参考](../REFERENCES.md#langgraph)。

## 6. 接口与页面

P1 计划只实现四类操作：提交案例任务、查询任务状态、确认或拒绝方案、读取结果与轨迹。具体 HTTP 路径在实现时确定，目前没有可调用 API。

页面用于查看证据、候选操作、确认状态和验证结果。首版不做账号系统、计费、通知、复杂仪表盘或多用户协作。

## 7. 记录与评测的边界

运行记录应保存模型与工具调用、调用关联、耗时、退出原因、版本和实际结果；不保存 API Key。日志中的案例材料属于输入数据，不能覆盖系统配置。

正式评测的参考根因、参考修复和独立验证器不得进入文档索引、模型上下文、工具读取路径或可修改副本。评测协议在实现前冻结，详见 [评测规范](evaluation.md)。
