# 开发路线与验收

**当前状态：仅初始化完成，以下功能任务全部待做。** 优先级表示实现顺序；只有代码、复现步骤与验收结果同时存在，才将对应任务标记完成。本文不承诺固定工期。

## P0：形成可验证的排障闭环

| 编号 | 任务 | 依赖 | 完成判据 |
| --- | --- | --- | --- |
| P0-01 | 固定范围，制作首个真实故障 | 无 | 初始项目可重复重建，故障稳定出现，人工参考修复能通过独立验证；保存实际版本与输出 |
| P0-02 | 实现只读案例检查 | P0-01 | `inspect_case` 至少一个分支返回真实事实；坏配置、缺字段、未知案例有明确结果，检查前后文件不变 |
| P0-03 | 文档登记、切分与检索 | P0-01 | 来源、适用版本与片段位置可回查；开发查询可核验命中；未命中与版本不明不会产生伪造证据 |
| P0-04 | 计划、确认校验与副本验证工具 | P0-02 | `verify_candidate` 只执行允许操作；拒绝无效确认；固定验证识别真实成功和失败，原始模板不变 |
| P0-05 | 接入一个模型与 LangGraph | P0-02、03、04 | 完成诊断—候选方案—确认—验证流程；至少三类故障需要不同检查步骤，能追问并处理验证失败 |
| P0-06 | SQLite 持久化与重复请求处理 | P0-05 | 等待确认时进程重启仍可继续；材料变化使确认失效；重复完成请求返回已有结果；未知执行结果先核查 |
| P0-07 | 固定评测协议与开发集基线 | P0-01 起设计，P0-05 后运行 | 开发/测试按原始案例分组；规则脚本和 Agent 使用同一验证器及预算；开发集保留所有首次结果 |

### P0-01：从这里开始

- [ ] 选择一个最小案例，优先“解释器选错”或“依赖缺失”。
- [ ] 新增案例说明，记录实际环境、输入文件、触发命令和原始输出。
- [ ] 从相同模板重建至少两次，确认故障重复出现。
- [ ] 人工执行参考修复，记录必要变化。
- [ ] 编写固定的导入或应用检查：修复前失败、修复后通过；检查不能只判断安装命令退出码。
- [ ] 分开保存输入、参考答案与验证器，约定未来工具的读取边界。

先完成一例，再扩展到 5–8 个可稳定复现的开发案例。没有复现成功或缺乏客观验收的案例暂不计入评测。

### P0-02：先获取事实

- [ ] 只实现首例需要的 `check_type`，避免先写空壳分支。
- [ ] 解析 `pyproject.toml` 或实际解释器信息，输出结构化事实与证据来源。
- [ ] 覆盖缺少文件、格式错误、未知案例和无权访问路径。
- [ ] 记录检查是否产生修改；只读工具不承担修复职责。

### P0-03：让引用可以核对

- [ ] 首批收集少量高相关官方文档，逐步扩展；约 10–20 篇是规模目标。
- [ ] 保存 URL、采集日期、工具适用版本、标题位置与内容哈希。
- [ ] 建立词法检索，再在开发查询上比较一种 embedding 检索。
- [ ] 使用真实查询核验片段能否支持结论；找不到时返回无证据。
- [ ] 依据开发集失败决定是否保留向量或混合方案，不默认增加重排器或向量数据库。

### P0-04 与 P0-05：把工具接成闭环

- [ ] 为工具参数与结果定义结构，错误参数在副作用前被拒绝。
- [ ] 在程序端保存候选操作，展示计划后再接受确认。
- [ ] 明确枚举、允许参数、工作副本、执行时限和固定验证入口。
- [ ] 接入一个真实模型；模型选择工具，程序执行函数与回填结果。
- [ ] 处理工具失败、模型异常、输出过大、预算耗尽和无法解决。
- [ ] 演示一次缺少信息时追问，以及一次验证失败后利用新证据调整或停止。

### P0-06：明确恢复能保证什么

- [ ] 确认绑定计划内容和相关文件状态；任一改变使旧确认失效。
- [ ] 使用持久化检查点验证等待确认阶段的跨进程继续。
- [ ] 验证两个任务的状态隔离。
- [ ] 已完成的重复请求不重复修改；结果不明时进入核查状态。
- [ ] 在文档中记录实际支持的恢复位置，不写“任意崩溃自动恢复”或“恰好一次执行”。

### P0-07：先冻结评测规则

- [ ] 按 [评测规范](evaluation.md) 固定案例分组、验证器、预算与结果字段。
- [ ] 先在开发集比较规则基线和完整 Agent，保留失败与首次运行。
- [ ] 预留测试集，不依据正式测试结果调提示词、检索参数或规则。

### P1 的交付检查

- [ ] README 中的启动命令在干净环境执行过，版本与真实依赖一致。
- [ ] 所有宣称已支持的工具分支都存在真实实现和验收记录。
- [ ] 参考答案和验证器没有暴露给运行中的 Agent。
- [ ] 报告以实际样本数表示完成情况，没有预设完成率或提升比例。
- [ ] 若邀请同学试用，只记录真实参与和真实反馈；试用不是完成项目的前置条件。
- [ ] 项目讲解能说明一条成功轨迹、一条失败轨迹和一次设计取舍。

## 后续按证据选择

MCP、第二个模型、重排器、更多故障类别与本地模型均属于后续选做。只有现有案例暴露了具体需求，再增加相应范围。

首版不安排微调、强化学习、多智能体、复杂前端、云端集群或复杂 CI。任务受阻时先缩小故障范围，保留真实可运行的闭环。

## 如何记录进展

每完成一项，在实际提交中补充代码、执行方式和结果，并更新本文状态。不要用一个始终返回成功的测试、静态演示 JSON 或未运行的截图代替验收。

EnvDesk 的开发进度与 MiniLoop 分别记录；实现另一项目的运行机制不自动证明 EnvDesk 已接入相同能力。
