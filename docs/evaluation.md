# 评测规范

**状态：评测设计，尚未执行。** 当前没有案例集、评分脚本或测量结果。本文用于实现时固定口径，不代表已达到任何指标。

本文与 [Code Design Spec 1.0](spec-v1.0.md) 配套。具体状态、执行边界、验收编号与阶段退出以 Spec §7、§9、§13–15 为准。

## 1. 评测问题

评测要回答：在明确限定的 Python 环境与依赖故障中，EnvDesk 能否根据证据判断原因、选择允许操作并通过独立验证？它相对于固定诊断规则的收益和成本是什么？

AI native 的行为证据按 Spec AI-01/02 验证：相似报错下根据实际事实选择行动，信息不足时针对性取证或追问，新证据或验证失败后更新判断并继续或停止。检查模型实际输入、工具轨迹和路由，避免由案例编号/隐藏类别预设根因；不要求不同案例机械地产生不同调用顺序，也不以调用次数多作为更自主的证明。

结果只适用于记录的环境、版本和案例集合。少量合成或人工构造案例不能证明对任意企业项目具有相同效果。

## 2. 案例与环境

先人工确认 5–8 个故障可复现，再逐步建立约 10 个开发案例与 20 个正式修复测试案例；数量是计划目标，报告时写真实数目。

每例至少记录：

| 字段 | 内容 |
| --- | --- |
| 标识与分组 | `case_id`、原始项目或根因实例的 `group_id`、故障类别、集合归属 |
| 环境 | 操作系统、Python、uv、依赖与缓存/网络条件 |
| 起始材料 | 配置、日志、触发命令、模板及其内容哈希 |
| 允许动作 | 操作枚举、可变更文件、参数约束、调用与时间预算 |
| 参考信息 | 人工核验根因、参考修复、独立验证条件及来源 |
| 记录 | 模板复现与参考修复的原始输出 |

同一案例的换名、日志改写或轻微配置改动不能跨开发与测试分组。开发和测试可以有同一故障类别，但应来自独立的根因实例，并公开说明构造方式与局限。

正式修复测试集只包括事先确认在允许操作内可解决的案例。缺少信息、拒绝确认、越界请求和恢复异常另设行为验证集，不混入修复完成率的分母。集合归属在执行前确定，不能看到失败后把案例挪出正式集合。

行为集还须包含正常环境与应用逻辑错误；“无需修改”不计为成功修复。开发案例应包含相同错误文本、不同环境根因的配对，避免固定执行同步操作即可覆盖全部案例。案例编号、目录名、分类与按答案裁剪的可用动作不能泄漏根因。

## 3. 最小防泄漏约定

1. 将起始输入与参考答案分开组织。运行中的 Agent 只能读取登记的输入及副本；参考根因、修复脚本、评分规则细节和独立验证器不进入模型上下文或检索索引。
2. 文档索引可以包含正常的官方知识，但不得混入测试案例的答案与结果报告。
3. 在开发集上调整提示词、规则、检索、工具和预算；冻结方案版本后再运行预留测试集。
4. 若要比较改进前后版本，先保留两个冻结版本，再对同一预留测试集做一次正式比较，不能看一次测试失败就继续调参。
5. 看过测试结果后若进一步针对这些案例改进，相关案例视为开发材料；另设未见案例才可再次声称做了未见测试。

个人项目很难做到作者完全不知道自己构造的案例。报告应据实说明由谁构造、标注和查看过材料；分组与冻结协议用于减少偏差，不能声称消除了所有泄漏。

## 4. 基线与公平比较

首个比较为“固定诊断规则脚本”与“完整 Agent”。规则基线应有实际实现，并能依据同样的环境事实工作；不能故意采用明显无效的固定答案。

两者使用同一初始案例、可访问证据、操作集合、验证器、每例最长执行时间和工具调用上限。每次运行从干净副本开始，避免使用前一方案已经修复的环境。

固定并记录模型与版本、提示词版本、文档快照、工具版本、配置、网络/缓存条件及失败处理规则。规则脚本没有模型开销，直接记录为零；不虚构等量模型调用。

增加 B1“固定事实采集与检索 + 同一模型单次生成计划”对照时，不允许根据执行反馈重新规划。它不阻塞首例闭环；若正式报告宣称多步诊断带来收益，则须在正式评测阶段完成此对照。仅运行规则与 Agent 时，结论限定为这两种实际方案的比较。

自动评测可以模拟用户确认，但批准规则必须事先声明，只依据范围与有效确认条件，不根据参考答案选择“正确”方案。真实人工拒绝、过期确认与恢复行为单独验证。

无人正式修复评测不提供临时人工答复；必要合法信息应已存在于输入和只读工具。进入 `needs_input` 时立即记为 `unresolved / needs_input_unanswered`，保留在正式分母中。追问质量另在行为集验证。

## 5. 指标与分母

| 指标 | 计算方式 | 需要同时披露 |
| --- | --- | --- |
| 修复完成率 | 原故障消失、固定应用/导入检查通过且约束保留的案例数 / 全部正式修复案例数 | 先写 `x/N`，再写百分比；超时、无结果、验证失败均保留 |
| 诊断正确率 | 与预标根因一致且证据充分的案例数 / 全部正式修复案例数 | 推测命中但证据不足的单列；无结果计为失败 |
| 引用正确率 | 支持对应结论且版本适用的引用条数 / 所有提供的引用条数 | 需引用却缺失的结论数；没有提供引用时该比率记为不适用，不记为满分 |
| 检索命中 | 正确证据进入前 `k` 条的查询数 / 全部已标注查询数 | `k`、查询集、文档快照与切分方式 |
| 端到端延迟 | 开始至最终状态的耗时，报告所有尝试的 P50 | 原始逐例耗时；失败与超时单独标记，不能仅保留成功样本 |
| 调用开销 | 每例模型调用数、工具调用数、接口实际返回的 token 数 | 缺少 token 数据时标为缺失，不据此猜测费用 |

若没有正式案例，完成率与诊断率记为未测；空分母不返回零或百分之百。引用核验应检查具体结论和片段内容，不只判断链接存在。

修复验证不能只看命令退出码，也不能允许方案通过删除功能、放宽原有约束、删除失败测试或篡改验证器取得成功。

检查和验证不得隐式同步依赖、改锁或替换环境。验证直接使用原业务入口及已确认的环境绑定；默认 `uv run` 不能作为验收启动捷径。成功必须对应当前任务、副本和执行后的材料指纹。

修复完成率由固定验证器自动评分。诊断与引用正确性在 1.0 先逐例/逐条人工核验，记录评分人及判据，不能称为自动或第三方独立评分。诊断标为正确、部分正确、错误或无诊断；部分正确不计入严格正确率。引用版本适用性未知时，不计作已确认正确。

## 6. 运行协议

1. 固定案例清单、验证器、预算和被评测版本，记录版本与哈希。
2. 重建初始副本，保存实际环境。
3. 运行方案并记录完整工具轨迹、耗时和退出原因。
4. 使用独立验证器判断；方案自述不能作为成功标签。
5. 保存每例首次尝试，统一汇总成功、失败、超时和无结果。

如果需要研究随机性，预先指定子集和重复次数，单独报告全部重复结果；不要取最好一次替代首次结果。外部安装服务或网络异常也需记录，是否重跑按事先制定的规则处理，并保留原始失败。

一次“首次运行”可以包含协议允许的预算内重新规划；整个任务失败后重建多次再挑最好结果不符合本规范。1.0 运行期使用固定离线资源。正式案例清单冻结后的 `setup_failed` 仍保留在主指标 N 中，单列为准备失败，不归因于模型根因判断；只有冻结前可以排除未通过复现检查的案例。

首次正式报告至少保存两个完整失败分析：故障现象、原始轨迹、判断失误、相关改动与复测结果。若没有两例实际失败，报告实际数量，不人为编造。

## 7. 独立行为验证

| 行为 | 完成判据 |
| --- | --- |
| 条件不足 | 明确请求缺失信息，不凭空补全版本与配置 |
| 用户拒绝 | 不执行修改，任务进入明确结束状态 |
| 确认过期 | 计划或文件改变后旧确认不能执行 |
| 重复提交 | 已完成请求返回已有结果，不重复产生修改 |
| 等待确认时重启 | 以同一任务标识恢复，两个任务状态不混淆 |
| 操作结果不明 | 进入核查流程，确认实际状态前不盲目重试 |
| 越界操作 | 未允许路径、命令或参数在执行前被拒绝 |
| 工具与模型错误 | 失败可解释，预算限制能终止循环并保存记录 |

这些验证与正式修复率分开汇总；它们证明执行机制的具体行为，不等价于任务成功率。

## 8. 计划生成的评测材料

实现时再添加案例清单、独立验证器、逐例 JSONL 结果和报告。每条结果至少关联案例、方案版本、环境、终止状态、验证结果、耗时、调用数和证据。

公开展示前核查不包含密钥、个人路径或私人仓库内容。发布报告时同时说明案例来源、构造方式、集合划分和局限；没有真实用户试用时不填写使用人数或业务收益。
